## 新增判断

1. 协议 v0.1 目前是「给人读」的规格，还不是「给运行器执行」的规格。第 4 节结束条件（"已形成明确方案"）和第 5 节（"避免同一轮重复执行"）都缺少机器可判的字段——这是上层运行器落地前必须先补的钩子，否则自动 Runner 无法可靠决策。
2. 单靠 Markdown 文本无法区分「本轮新观点」和「历史回声」。协议要求每轮必须产生新信息，但缺少可校验的载体（结构化字段 + diff），运行器无法自动验证一轮发言是否有效。

## 具体改进方案

### 方案 1：在 status.md 引入「回合账本」（Event Ledger）
在现有字段（Round / Last writer / Next writer / Status / Completion）之外增加一个账本字段，例如：

- `Last event: R2-DOUBAO-<内容哈希前8位>-<时间戳>`

运行器每次启动时对比自己的执行日志：该 event id 已处理则跳过（幂等），未处理才执行并记录。这把协议第 5 节的「避免同一轮重复执行 + 保存执行日志」从原则变成可执行规则，同时利用 GitHub 写文件带 SHA 乐观锁的特点，天然防止并发覆盖。

### 方案 2：意见文件统一为「可解析模板」
把 doubao.md / gpt.md 统一为 front matter + 固定小节：

```
---
round: <n>
writer: <GPT|Doubao>
date: <YYYY-MM-DD>
adds: <true|false>
---

## 新增判断
## 对对方的回应
## 改进方案
## 待确认问题
```

运行器可确定性解析：只有 `adds=true` 且对应文件 diff 非空，才视为有效发言，否则判定为「空转」并告警。

### 方案 3：结束条件操作化
把协议第 4 节的结束条件改写成运行器可判定规则：

- 仅当「待确认问题为空」且「tasks.md 已写入本次结论对应的任务更新」时，才允许置 `DONE`；
- 若某一方认为需要用户裁决，置为新增状态 `NEED_USER_DECISION`，而不是直接结束或无限继续。
